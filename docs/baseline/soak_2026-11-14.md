Connector v2 (`research/live/feed_bridge.py`) and a fresh server, five symbols (BTCUSDT, ETHUSDT, BNBUSDT, SOLUSDT, XRPUSDT), run with `uv run python -m research.live.soak --hours 26 --out data/soak/2026-11-14` on the development PC (Windows 10, home connection). Started 2026-11-14 05:52:05 UTC, ran 26.0 h, 1,560 checks. The criteria are in [docs/live_platform_architecture.md](../live_platform_architecture.md) (soak test, P7.8); the verdict file is [soak_2026-11-14.json](soak_2026-11-14.json).

**Verdict: `pass: false`, accepted (user's decision, 2026-11-15).** Four of the five criteria passed. The fifth, resync time, failed during a loss of the PC's own network connection; once Binance was reachable again every resync took under 10 s. The run is accepted with that outage recorded as an external event, and two things it didn't show are listed below and in the changelog's known limitations.

## The outage (2026-11-15, 09:59-10:07 IST)

From `bridge.out`: depth updates stopped at 09:59:25 (10 s silence → `gap` on all five symbols); reconnects then failed with opening-handshake timeouts and `getaddrinfo failed` (DNS lookups on the PC failing), a connection held from 10:01:17 to about 10:04, then the same again with a `keepalive ping timeout`, two more failed attempts, and a short-lived connection, until a stable one at 10:06:59. The bridge needed no intervention.

Time from `connected to Binance` to all five symbols synced, for the three reconnects: 8.2 s, 9.5 s and 8.1 s. The 100-116 s resyncs counted from the gap are almost entirely time without a network. Nothing was logged at warning level after 10:07.

The drop at hour 23 is the outage: the feed's books were reset and rebuilt from snapshots, and the memory went with them, so the growth was state the server holds for the live books, not lost memory. Whether that state stops growing on a long connection was not shown (below).

## Not shown

- **Binance's own 24 h close.** Binance closes each connection 24 h after it opens; the outage replaced the connection about 80 minutes before that. The reconnect after an outage goes through the same path (connection lost → `gap` → reconnect → snapshot), and that path recovered three times, but the clean close itself was not observed.
- **Bounded server memory on one long connection.** About 2.3 MB/h for 22 h before the reset (18 → 57 MB), within the criterion, but the run doesn't show where it levels off. The likely candidate is price levels kept in the live books as the price moves; to check with the server's per-symbol level counts.
